# 正文深度示例：Skill 文件包校验器

本例根据本 Skill 自带校验脚本编写，是展示写法的局部技术说明，不是目标业务系统的完整 4+1 文档，也不能替代真实项目试用。阅读正文无需打开任何链接；源码定位集中在末尾。

## 使用场景与运行方式

维护者修改 Skill 后，需要确认分发包所引用的文件没有遗漏，主入口元数据符合约定，Markdown 中的本地资源链接仍然有效。校验器在维护者的本机或 CI 工作目录运行，不启动业务服务，也不部署到远程现场。它只读取 Skill 目录，检查结束后输出一条 JSON 结果。

运行环境需要 Bash 和 Python 3.9 及以上版本。Bash 入口从自身所在目录向上确定 Skill 根目录，因此调用者不必先切换到 Skill 目录。Python 解释器默认使用 python3；如果本机的 python3 指向不可用的 Windows 商店别名，可以通过 PYTHON 环境变量指定已有解释器。这个设置只改变校验器的执行环境，不改变被检查的 Skill 内容。

## 架构说明

校验器由 Bash 启动层和内嵌 Python 检查层组成。Bash 负责确定目录、选择解释器、向标准错误输出检查提示；Python 负责检查文件、入口和链接，并把发现的问题汇集成结果。两层串行执行，没有后台任务、队列或持久化状态。一次运行只检查当前 Skill 包，不扫描目标项目源码。

Bash 把根目录作为参数传给 Python，内嵌代码通过标准输入执行。这样检查层不依赖调用时的工作目录。所有正常发现的结构问题累积到同一个列表，维护者可以在一次运行中看到多个问题，而不必每修复一个文件就重新发现下一个缺失项。

## 详细设计

检查开始时，Python 将传入目录解析成绝对路径，并创建问题列表。首先遍历脚本内置的必需资源清单，逐一检查主入口、说明、视图指南及模板是否为文件。缺失资源会产生包含资源相对路径的问题信息。这个清单证明指定资源齐备，不代表 Skill 中所有可能使用的文件都已自动识别。

随后读取主入口，要求文件从 YAML 风格的 frontmatter 开始。当前实现用正则提取单行 name 和 description，而不是通用 YAML 解析器：name 必须与目录名一致；description 必须存在、长度不超过 1024 字符，并包含 Use when。修改为多行或复杂 YAML 时，即使其他客户端可以加载，也不一定满足这个检查器的有限约定。

第三步递归读取 Skill 目录中的 Markdown 文件，提取形如 Markdown 链接的目标。带 URI scheme 的目标和没有路径的纯锚点会跳过；本地路径相对当前 Markdown 所在目录解析，并进行 URL 解码。解析后的目标必须仍位于 Skill 根目录之内，而且是实际存在的文件。因此，指向不存在资源的链接与越出包目录的链接都会被记录为问题。带文件路径的章节链接会检查文件是否存在，但不会检查锚点是否真的定义；纯章内锚点也不会验证。

最后检查主入口是否保留“场景和物理视图必须合并组织”及“开发视图必须同时具备架构说明和详细设计”两条核心规则。这只是字符串级检查，不能证明后续生成的文档遵循了规则，更无法判断正文是否详细、流畅或准确。

## 结果、异常与限制

正常完成检查后，标准输出包含 ok、markdown_files、local_links_checked 和 issues 四个字段。问题列表为空时，ok 为 true，进程以 0 退出；存在结构问题时，ok 为 false，进程以 1 退出。CI 可以使用退出状态判定包结构是否合格，同时保留 JSON 供维护者查看具体问题。标准错误上的启动提示不会混入正常 JSON 输出。

不是所有执行故障都能形成 JSON。解释器不存在时，Bash 无法启动检查层；文件无法读取、编码无效等未捕获异常也可能中断 Python。此时应依据实际退出状态和错误信息修复运行环境或文件问题，不能把“没有 JSON 问题列表”视为检查通过。

脚本不创建临时文件，不修改被检查内容，也不自动修复链接。它适合分发前的结构检查；生成文档的事实正确性、说明深度、图文一致性和现场部署仍需要另外审阅与验证。
