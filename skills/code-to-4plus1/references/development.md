# 开发视图：架构说明与详细设计

## 两层内容都写在正文

每个范围内模块以真实名称组织，在主文档的开发章节内提供架构说明和详细设计。缺任一层即未完成；无需 MOD / ARCH / DD 编号或额外设计页面。范围外模块明确列出，不能默默缩小范围。

架构说明讲清职责边界、上下游、依赖方向、接口协作、扩展点、工程与构建组织，以及服务的场景。总体架构用实际功能解释跨模块协作，不能只有目录图。

详细设计讲清输入输出与校验、数据语义、流程、算法与规则、状态变化、持久化、配置分支、错误处理、事务并发与生命周期。以实际复杂性决定深度；不适用的机制不硬凑章节。关键语义必须写在正文，不能只给链接或函数签名。

## 分析与解释

- 读取入口、接口、实现绑定及调用方，确认真实职责及路径，不按命名猜行为。
- 对关键处理说明“接收什么、检查什么、满足什么条件走哪条路径、修改什么、返回什么”。条件与边界值来自源码。
- 接口说明参数含义、验证、返回和错误；字段多时可列表，但解释字段如何参与处理、约束和状态。
- 数据说明关系、约束、读写时机、状态及失败后的影响，不把数据库字段转抄当设计。
- 关键算法与状态机逐步展开；配置解释默认、覆盖顺序及对场景的影响，不只列键名。
- 并发、事务、异常、取消、重试及资源释放按实现讲清，不能笼统写“保证一致性／自动恢复”。
- 构建和测试区分仓库声明与实测。动机有记录才作为事实，推断和改进建议明确限定。

## 深度与联系

读者应能据正文理解并定位如何修改关键行为，而不必先读源码。复杂模块仅有一两句职责或函数列表不合格，需要继续追踪；无需逐行翻译访问器和复制全量代码。

用实际名称解释场景步骤如何进入模块、如何经过架构接口到实现、如何产生结果。源码证据集中附录。共享机制可在相应模块完整描述，其他场景仍保留理解本场景所需的背景，不能只有“详见”。

大项目分批扩写同一主文档的开发章节，不能先生成几十份空页并称为完成。未覆盖设计明确说明并继续完成可处理内容。
