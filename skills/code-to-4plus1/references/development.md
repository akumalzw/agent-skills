# 开发视图：架构说明与详细设计

## 必需的两层

为每个纳入范围的模块建立 MOD-*，同时提供 ARCH-* 架构说明与 DD-* 详细设计。缺任一层即为该模块未完成；范围外模块单列，不通过缩小统计口径隐藏遗漏。

架构说明包含：职责与边界、上下游、依赖方向、对外契约、协作方式、扩展点、工程与构建组织、适用场景。总体架构解释跨模块协作，不只罗列目录。

详细设计包含：输入输出与校验、关键数据结构、处理流程、算法与业务规则、状态变化、持久化、配置分支、错误与恢复、事务并发、资源生命周期。某项不适用时写明原因；关键语义不能只用源码链接代替解释。

## 从代码还原

- 读取架构接口、实现绑定及主要调用方，确认实际职责和依赖方向。
- 对关键功能沿入口追踪到结果与异常，记录符号、分支条件及证据。
- 接口描述覆盖参数语义、返回、错误、边界、版本或兼容条件；契约和实现冲突分别记录。
- 数据设计关注字段语义、约束、关系、状态和读写行为，不机械抄字段清单。
- 配置说明覆盖默认值、来源优先级、读取与使用点及场景差异。
- 构建说明区分仓库声明的命令与实际执行结果；没有运行则标未验证。
- 设计动机有记录才作为事实引用；从实现推导的动机标推断。未来改进建议与当前实现分开。

详细设计的深度以“读者能据此定位、理解并修改关键行为”为准，不要求逐行翻译、穷举无逻辑访问器或复制全量代码。

## 贯通要求

SC-* 场景步骤 → CAP-* 能力 → MOD-* 模块 / ARCH-* 架构接口 → DD-* 处理规则 → 源码符号 / E-* → 验证。

架构接口必须有实现详述或明确外部边界。每个 DD-* 要能回溯职责与适用场景；无现场信息时关联候选场景。共享详细设计复用一份，场景仅说明配置和路径差异。最终检查架构与实现一致，不能以架构图替代详细设计，也不能以函数清单替代架构说明。
