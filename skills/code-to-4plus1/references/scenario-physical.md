# 场景与物理视图

## 组织原则

场景是主线，物理部署内嵌于场景。场景包括业务目的、现场使用条件和部署条件。为场景分配 SC-*，为部署变体分配 DP-*，为运行实例分配 RI-*。同一场景可绑定多个部署变体，同一部署可支撑多个场景；共享部署定义需在每个场景呈现适用条件、实例绑定、配置与执行路径。

初次只有程序时状态为“候选场景／现场待确认”。不得把源码支持的部署可能性写成现场现状。

## 每个场景的分析

1. 记录目标、触发者、输入输出、前后置条件、环境约束、适用版本与来源。
2. 对每种适用部署方式，记录程序或制品、节点角色、运行实例、网络连接、外部系统、存储及配置来源；未知节点数量或地址可留未知，不补造。
3. 从实例绑定到启动入口，追踪配置键、优先级、功能开关和代码分支；声明配置与现场生效值分开，敏感值不记录。
4. 从场景触发追踪到结果，覆盖关键异常与恢复：失败分支、超时、断连、重复消息、重启后的状态等，适用性以实现为准。
5. 每步绑定能力、模块、架构接口、详细设计、符号位置与证据；在异步边界标记生产者、传输通道、消费者与失败行为。
6. 比较部署变体带来的通信、配置、并发和数据路径差异，引用对应逻辑、进程和开发说明。
7. 记录现场验证时间、环境、程序版本、结果与限制。无法关联源码版本时说明映射尚未验证。

## 图示

按需给出部署拓扑和时序／数据流图，复用同一 RI-* 实例标识。节点表示实际运行单元，类不是进程；箭头注明协议、同步／异步及方向。候选、声明、推断使用图例并在文字中说明。跨实例交互同时给出对应代码及配置依据。

## 完成条件

读者从场景页可以明确部署在哪里、运行什么、配置如何影响路径、结果由什么代码产生、现场确认了什么。无现场证据时允许形成源码草稿，但现场关联状态必须保持待确认。
