# 场景与物理视图

## 组织原则

场景是主线，物理部署内嵌于场景章节。用现场、程序、模块和实例的自然名称叙述，不强制 SC / DP / RI 编号。同一场景可有多个部署变体，同一部署也可承载多个场景；要直接解释具体绑定、适用条件和差异，不能让读者靠矩阵和引用拼接。

初次只有程序时明确为候选场景，现场待确认。完整展开代码可确认的行为，不因现场缺失而只交付几句概括；不得把源码支持的部署可能性当成现场事实。

## 每个场景的分析与成文

1. 说明目标、触发者、输入输出、前后置条件和使用约束，给读者足够背景。
2. 将程序、节点角色、实例、网络、外部系统和存储放入同一部署说明；未知信息集中交代，不补造地址和节点数。
3. 从实例启动追踪配置键、覆盖顺序、功能开关与代码分支，解释它们如何改变流程；声明和现场生效值分开，秘密不记录。
4. 连续叙述从触发到结果的完整链路，说明校验、分派、计算、读写及反馈；关键步骤解释数据和状态如何变化，不能只列模块名或调用箭头。
5. 展开重要失败和恢复，说明错误如何反馈、是否留下部分结果、重试或重启会怎样；没有保障时明确限制。
6. 对不同部署方式，解释通信、并发与数据路径的具体差别。当前章节要能独立读懂，深入实现可在正文说明后提示开发章节。
7. 源码定位按主题归入主文档附录；现场验证说明环境、时间、版本、结果及限制。无法映射版本时不冒充已确认。

## 图与完整性

拓扑、时序和数据流图使用一致且有意义的名称；类不是进程，箭头注明协议和同步／异步。图前后解释节点职责、关键交互、分支及影响，不能靠图代替叙述。候选或推断用图例和自然语言限定。

忽略所有链接后，读者仍能说明“为什么运行这个场景、在哪里运行、怎样处理、结果是什么、失败怎么办”。达不到就继续分析和补写正文。
